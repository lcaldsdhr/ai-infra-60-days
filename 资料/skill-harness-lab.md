# Skill 与 harness 实战练习

本轮实际使用了 skill-creator、openai-docs，查阅官方文档并创建 research-to-code。本文件是学习说明，不是持久化 agent 指令。

## 什么放在哪里

| 内容 | 位置 | 示例 |
| --- | --- | --- |
| 本次目标与验收 | 当前提示 | 加入流式响应，断开连接时停止后台工作 |
| 项目通用约定 | AGENTS.md | 包管理器、项目必需的检查命令 |
| 某类任务的复用方法 | SKILL.md | 查证版本、形成决策、实现与验证 |
| 按需读取的专门知识 | references/ | 内部协议、数据库关系 |
| 反复执行的确定操作 | scripts/ | 将评测日志转成统一格式 |
| 输出需要的素材 | assets/ | 文档模板、项目脚手架 |
| 工具、权限、运行和反馈机制 | harness 或其配置 | 浏览工具、shell、测试运行器 |

这里 harness 是运行框架的概念，不是某个名为 harness 的 Codex 配置文件。Skill 可以指导使用工具，但不会新增工具或扩大权限。

## 调用你刚创建的 skill

在支持 `$` 的 skill 选择界面中选择它，也可使用当前界面提供的技能选择器：

```text
$research-to-code
项目：<绝对路径>
目标：为现有接口加入流式响应。
需要查证：项目所用框架版本如何处理流式输出和取消。
验收：逐段收到数据；客户端断开后停止后台工作；普通响应不受影响。
约束：沿用现有鉴权和依赖版本。
```

若选择器暂时看不到，直接指定文件：

```text
读取 C:\Users\34739\.codex\skills\research-to-code\SKILL.md，
按照它完成下面的任务：<目标、项目路径、约束、验收>。
```

显式调用方便学习与排错。自动选择主要依赖 description；结构校验通过不表示当前会话的 skill 列表已刷新。必要时重新打开会话或重启应用后检查。

## 如何构造自己的 skill

1. 从重复发生的真实任务开始，写出输入、输出和一个验收例子。
2. description 写“处理什么、何时使用”；容易误触发时加入边界。避免“帮助所有开发和调研任务”。
3. 正文保存会改变决策的知识：版本如何确认、证据如何处理、何时停止、失败如何反馈。
4. 只在需要时加 references、scripts、assets。初版没有这些目录也完全合理。
5. 用真实请求试用，依据失败证据做最小修订。

本例最值得看的是“剩余未知项不再影响验收时结束检索”，以及“把关键假设变成可观察检查”。它们让调研服务于实现，同时给 agent 明确反馈。

## harness 的反馈闭环

```text
目标与项目上下文 → 加载 skill → 查证与实施 → 验证结果
                       ↑                       ↓
                       └──── 根据证据调整 ──────┘
```

开发反馈可以来自测试、类型检查或实际运行；调研反馈可以来自来源是否支持结论、版本是否适用、证据是否冲突。

例如“最新版文档支持取消”仍不足以指导旧项目。先确认安装版本，再检查实际断开行为。若实验发现后台任务继续执行，应调整实现并重新验证。

复杂任务可以记录“问题 → 来源/版本 → 发现 → 实现影响 → 检查结果”。简单任务无需因此创建报告。

## 用什么任务评价

下面是建议评估用例，尚未作为独立行为评测执行：

| 请求 | 期望行为 |
| --- | --- |
| 查框架 SSE 行为并加入流式接口 | 适用；查对应版本并验证行为 |
| 查兼容性再升级依赖并修复调用 | 适用；证据影响升级方案，运行相关检查 |
| 把按钮文字改成保存 | 通常无需此 skill，直接完成 |
| 只写领域文献综述 | 通常无需此 skill，保持纯调研范围 |
| 文档与本地结果冲突 | 检查版本及前提，保留可复现实验 |
| 无网络且缺关键资料 | 说明证据缺口，不捏造引用或检查结果 |

比较修订前后有没有误触发、关键判断是否有证据、是否完成验收、有没有无用检索。不要只检查标题和输出格式。

结构校验仅检查基础格式，不能证明行为质量。这个初版还需要用你的实际项目评估。

## 后续迭代的调用示例

```text
$skill-creator
改进 research-to-code。原始请求、实际输出和失败证据如下：……
请定位是触发描述、缺失知识还是执行流程的问题，
做最小修订，再用同一任务检查效果。
```

不要因一次版本错误就要求每次检索十个来源。增加针对性的版本核对规则即可；只有反复出现相同机械操作，才值得新增脚本。
